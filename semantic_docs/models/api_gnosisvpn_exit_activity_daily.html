api_gnosisvpn_exit_activity_daily

GnosisVPN traffic by exit node and country, per day -- the SUPPLY side of the product. Works because the exit-node roster is committed to git (gnosis/gnosis_vpn linux/resources/config-jura.toml) with an address, city and country per destination. Scoped to jura, which carries no cover traffic. The demand side -- how many clients exist and how many actually used it -- is api_hopr_gnosisvpn_users_daily; neither answers the other's question. Three caveats travel with this data. Tickets are probabilistic payments, proportional to relayed volume in expectation but NOT a bandwidth measurement (real bytes live only in node-local Prometheus metrics). Channel counts track how many clients are running, not usage, because the client auto-maintains channels toward target_open_channels -- read tickets_redeemed for usage. And the city/country labels are product metadata, not verified geography: the announced IPs cluster in one 185.9.1.0/24 block plus Google Cloud ranges. The exit roster is a static git snapshot, so it goes stale silently as HOPR adds exits -- unlike int_hopr_vpn_clients, which is derived structurally.

country_codeLowCardinality(String)ISO-3166 alpha-2 of the exit node's advertised location.

exit_labelStringHuman label for the exit from the GnosisVPN client config.

redeemed_wxhoprDecimal(38, 18)wxHOPR paid out to this exit, from channel balance decreases.
tickets_redeemedUInt64Redeemed tickets on channels terminating at this exit. The usage series -- proportional to relayed traffic in expectation, not a byte count.
unique_counterparty_nodesUInt64Distinct nodes funding channels toward this exit. An upper bound on running clients, not a user count -- one operator can run many nodes, and this is per-exit so it cannot be summed across exits.
