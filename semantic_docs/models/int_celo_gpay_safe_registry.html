int_celo_gpay_safe_registry

GP card Safes on Celo, discovered natively: a Safe that emits EnabledModule(<GP Roles proxy>) has been provisioned as a GP card (replaces the fp CTE of Dune query 7808895). Confirmed pre-spend, so this also covers created-but-never-funded cards. address/contract_type columns follow the whitelist shape the decode macros expect via contract_address_ref. Cardinality is 1:1 with int_celo_gpay_roles_modules and grows continuously with issuance (1815 on 2026-08-05); first card 2026-03-31. POPULATION = THE UNION OVER EVERY IN-SCOPE SETTLEMENT CONTRACT, seeded in celo_gpay_settlement_contracts. Two AggregateBridges are live at once and both are Gnosis Pay's (confirmed by GP 2026-08-05): settlement_legacy 0xc4df5cac… from 2026-03-31, which GP will migrate onto settlement_current 0xc07cd8c2… (from 2026-05-28) at an unannounced date. They are ONE card program, so they are unioned here. They share no event signatures and so need two ABIs to decode, but that is because the current one adds an indexed `sender` to every event, not because the contracts are unrelated — both are AggregateBridge with identical function selectors (established when the ABIs were fetched on 2026-08-06). Two generations of one design; the legacy/current labels describe lifecycle, not a published release lineage. Until 2026-08-05 this registry keyed on the current contract alone and therefore omitted 235 real cards and 1743 settlement transfers — roughly 34% of all settlement traffic and 13% of cards. The distortion was worst in shape, not level: March/April/May were ~100% missing, so the tree showed payments starting in June and rising 4 -> 266 -> 2533, when the program had in fact been running steadily since March at 4 -> 225 -> 472 -> 759 -> 3008. Any historical Celo GP figure produced before 2026-08-05 is understated and reshaped; restate rather than splice. Which bridge a payment settled to is a per-TRANSFER fact (int_celo_gpay_activity.settlement_address), never a per-card generation column — a migrating card keeps its legacy history and gains current-contract payments, so a card-level attribute would go stale on migration day. int_celo_gpay_roles_modules .wired_settlements is the migration tracker: a module listing both addresses has migrated. Zero had as of 2026-08-05. A third AggregateBridge 0xd11e35ca… is deployed but never used and NOT confirmed GP-owned; it sits in the seed as status='planned', excluded from discovery. Flipping it to 'active' is the whole change needed if it goes live. Completeness is now proven non-circularly, from settlement traffic on BOTH bridges: 507 current-contract spenders + 155 legacy spenders, zero missing from this registry (2026-08-05). The earlier "483 senders, all present" proof was circular — it defined the spender population using this model's own single bridge address, so it could not have detected a second one. Any future proof must start from the seed, not from one address.
