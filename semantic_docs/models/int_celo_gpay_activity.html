int_celo_gpay_activity

Per-transfer classified Celo GP activity. Classification happens HERE, not upstream — the single transfer base int_celo_gpay_safe_transfers_alltoken supplies transfers touching a GP card Safe (restricted here to whitelisted tokens via token_symbol IS NOT NULL, which drops CELO gas dust and spoof tokens). The base already resolves the card side (safe_address / direction / counterparty), so classification reads those directly (mirrors int_execution_gpay_activity on Gnosis Chain classifying from raw logs). "Bridge" here means ANY settlement contract seeded in celo_gpay_settlement_contracts (status active or migrating) — two are live and both are GP's. This set and int_celo_gpay_safe_registry MUST widen together: the registry decides which Safes exist, this model decides what their transfers mean, and widening discovery alone would book their settlement transfers as Withdrawals via the catch-all. Actions: Payment (card -> bridge in a STABLECOIN), Other (card -> bridge in a non-stablecoin whitelisted token — rare, excluded from payment metrics), Withdrawal (card -> anywhere else), Reversal (bridge -> card refund), Top-up (anything else -> card), and Cashback (a configured rewards disburser -> card in an RWA reward token). The token_class='STABLECOIN' gate on Payment keeps CELO/reward tokens out of card spend. Cashback is COMPILED OUT until the model's cashback_sources list is populated (cashback not paid yet), so reward inflows currently fall through to Top-up — a safe no-op scaffold. A Safe-to-Safe transfer would appear twice in the base (out + in); the model collapses to the sender ('out') side so each transfer is one row (a Withdrawal), matching prior sender-priority semantics. (No card-to-card transfers occur in practice on Celo GP.) materialized='incremental' insert_overwrite with apply_monthly_incremental_filter recomputes the whole current calendar-month partition every run, so a card recognized slightly late is reclassified within the month. A staged run with start_month set switches to append instead, so those batches must target empty months. int_celo_gpay_wallets stays a full rebuild; only this per-transfer model scales with tx volume.

This is the bridge dimension — slice payments by it to separate the legacy cohort GP is migrating from the current cohort, or to watch the migration land. Deliberately a per-TRANSFER fact rather than a per-card generation column: a migrating card keeps its legacy payments and gains current-contract ones, so any card-level attribute would be wrong from migration day onward.
token_addressStringTransferred token contract address (0x-prefixed, lowercase). Part of the grain, so it disambiguates two different tokens moving between the same pair in one tx.
token_symbolStringWhitelist symbol from celo_tokens_whitelist (USDT, USDC, USDm or XAUt0). Only USDT and USDC occur in the data as of 2026-08-03.
