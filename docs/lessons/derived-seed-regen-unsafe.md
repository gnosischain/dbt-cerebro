## Symptom
You run the documented refresh step for a generated seed. It reports success. Either a
decoded model then rebuilds to zero rows with no error, or nothing appears wrong at all
until some unrelated contract quietly stops decoding weeks later. The diff is thousands
of lines because the generator reorders as well as regenerates, so nobody reads it.

## Root cause
Three failures that all hide inside "the generator ran fine", and the third is what let
the first two survive.

**Position-slicing a hex string across a library upgrade.** `HexBytes.hex()` returned a
`0x`-prefixed string up to hexbytes 0.x and returns it bare from 1.0. Code that strips
the prefix with `[2:]` keeps working syntactically and starts eating real payload. For a
32-byte topic0 you lose two hex characters; for a 4-byte selector you get bytes 1–4
instead of 0–3. The output is still a plausible-looking hex string of nearly the right
length, and the failure surfaces as a JOIN that matches nothing.

**A derived artefact that is not actually derivable from its declared source.** The
seed was documented as generated from `contracts_abi.csv`, but rows had been retained
by hand after their ABIs were removed from the store. That inconsistency is invisible
while nobody regenerates, and the moment somebody does, the "regeneration" is a
deletion. The generator cannot warn you, because from its point of view those rows
simply do not exist.

**Nondeterministic output order, which is what made the other two undetectable.** The
generator wrote rows in source order, so an unrelated change to the ABI store reshuffled
the file and a two-row change presented as thousands of modified lines. Nobody reviews
that diff, so nobody would have noticed truncated hashes or deleted rows inside it. An
unreadable diff is not a cosmetic problem — it is the mechanism by which real defects
ship.

## Forbidden action
Do not commit a regenerated seed on the strength of the generator exiting 0. Do not
judge it by the line diff alone even now that ordering is stable — a diff being small is
evidence about ordering, not about content. Do not assume a generated file is
reproducible just because a script exists that claims to produce it.

## Detection
Compare as SETS against HEAD, not as text, and insist that the removed set is empty:

```python
old = set(subprocess.run(["git","show",f"HEAD:{path}"],capture_output=True,
                         text=True).stdout.splitlines()[1:])
new = set(open(path,encoding="utf-8").read().splitlines()[1:])
print("added", len(new - old), "REMOVED", len(old - new))   # REMOVED must be 0
```

Plus a shape assertion the corruption cannot survive — every event signature is exactly
64 hex characters, every selector exactly 8:

```python
bad = [r for r in rows if len(r["signature"]) != 64]
```

And one known-answer check, which is the cheapest of all: the canonical ERC-20
`Transfer(address,address,uint256)` must hash to
`ddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef`. If it does not, the
hashing is wrong and nothing else you generated is trustworthy.

## Safe remediation
Slice by prefix, never by position — `.hex().removeprefix("0x")` — so the same code is
correct on both library generations. Then make the source complete rather than patching
the output: restore the missing ABIs so the declared source really does produce every
row, and re-run until the removed set is empty. A generated file that cannot be
regenerated byte-for-equivalent from its input is not generated, it is hand-maintained
with extra steps, and it will lose data the first time someone believes the docstring.

Make the output deterministic in the same change. Sorting on identity (chain, address,
name, signature — never on the JSON payload columns, whose formatting is not stable) costs
one line in the writer and converts every future regeneration into a reviewable diff.
Verify it by regenerating twice and requiring the two files to be byte-identical; a
generator that is not idempotent cannot be reasoned about.

Order matters: `signature_generator.py` reads ABIs from the ClickHouse table, not the
CSV, so `dbt seed --select contracts_abi` must run BEFORE the generator or it silently
regenerates from a stale ABI set. The documented sequence is right; running the
generator first is the easy mistake.

## Ground truth
Known-answer vectors. Canonical event hashes and selectors are public and fixed —
`Transfer`, `Approval`, any well-known signature. A generator that reproduces those is
almost certainly right; one that does not is wrong regardless of how confidently it
reports success.

## Enforcement
Code fix in `scripts/signatures/signature_generator.py` (prefix-strip helper and a
deterministic sort in `write_csv`) plus the 4 restored ABIs, so regeneration is now
additive by construction and reviewable by default. No CI gate: the seeds
change rarely and legitimately, and a gate that fires on every genuine ABI addition
would be turned off. The durable protection is the set-diff above — run it before
committing any regenerated seed, and treat a non-empty removed set as a bug in the
source, never as an expected cleanup.
